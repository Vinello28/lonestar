# LoneStar — Engineering Lessons & Invariants

1. **Non-Bluish Warm Neutral Palette**: All background surfaces in both Light (`#f6f4ef`, `#fdfcf9`, `#eeeae0`) and Dark (`#161614`, `#1f1e1b`, `#282723`) modes maintain `R >= G >= B` to strictly avoid any cool/bluish tint.
2. **Clean Architecture Dependency Rule**: `lonestar-core::domain` has zero external UI/DB/framework dependencies. `application` depends only on `domain` traits (`ports`). `infrastructure` and `src-tauri` adapt external formats (piStar JSON, filesystem, Tauri IPC) to `application` use cases.
3. **iStar 2.0 Metamodel Fidelity**:
   - Actors (`Actor`, `Agent`, `Role`) cannot form `IsA` cycles or `ParticipatesIn` cycles (two independent constraints of guide §8: only edges of the same kind close a cycle, so a loop mixing both kinds is conformant), and `IsA` only connects matching non-Agent actor types (`Actor->Actor` or `Role->Role`). Role badges draw a downward smile arc at the bottom of the circle.
   - Internal intentional elements (`Goal`, `Quality`, `Task`, `Resource`) must belong to an Actor's Strategic Rationale boundary (`istar.boundary` error if orphan); `NeededBy` strictly maps `Resource -> Task` (terminating with a solid filled circle), `Contribution` maps `* -> Quality` (`make`, `help`, `hurt`, `break`, max 1 per pair; only a Quality contributing to itself is forbidden, mutual Quality↔Quality contributions are valid and must not be rejected), `Qualification` maps `Quality -> Goal/Task/Resource` (mutually exclusive with `Contribution` on the same element pair), and `AndRefinement`/`OrRefinement` map `Goal/Task -> Goal/Task` without cycles, without mixing AND and OR on the same parent (`MixedRefinementOnParent`), with >= 2 children recommended for AND (`istar.refinement.singleAndChild` warning), and without non-standard `"AND"`/`"OR"` text pills (explicit `Goal -> Task` refinements must be preserved).
   - Social `Dependency` links span two distinct actors (`depender` and `dependee`) through a `dependum` (`Goal`, `Quality`, `Task`, `Resource`), optionally anchored to internal elements belonging to those respective actors; a `dependerElement` cannot be refined or contributed to (`DependerElementCannotBeRefinedOrContributed`).
4. **piStar Compatibility**: Import must gracefully accommodate legacy piStar v2 JSON files (including minor warnings) and preserve visual coordinates and IDs round-trip.
5. **macOS Ad-Hoc Bundle Signing (`bundle.macOS.signingIdentity: "-"`)**: In Tauri v2, omitting `bundle.macOS.signingIdentity` skips running `codesign` on the `.app` bundle, leaving only the linker-signed Mach-O binary (`Info.plist=not bound`, `Sealed Resources=none`, no `Contents/_CodeSignature`) which fails `codesign --verify --deep --strict` (`code has no resources but signature indicates they must be present`) and causes macOS Gatekeeper to report the downloaded app as *"damaged"* instead of allowing execution via *Privacy & Security → Open Anyway*. Always set `"macOS": { "signingIdentity": "-" }` when no Apple Developer ID certificate is configured.
6. **GitHub Pages Two-Job Workflow (`build` → `deploy` with `needs: build`)**: Never run `actions/upload-pages-artifact` and `actions/deploy-pages` consecutively inside a single job. Due to eventual consistency in GitHub Actions' `ArtifactService/ListArtifacts` index right after upload finalization, `deploy-pages` in the same job can receive `Found 0 artifact(s)` and fail with `No artifacts named "github-pages" were found`. Always split `build` and `deploy` into separate jobs linked by `needs: build`, set `cancel-in-progress: false` in the `pages` concurrency group, and use Node 24-native action major tags (`upload-pages-artifact@v5`, `deploy-pages@v5`).
7. **Encode the spec in tests, not the implementation**: The Phase 15 tests asserted "contribution cycle between Qualities is rejected" and a mixed is-a/participates-in loop as an error, so they enshrined two rules stricter than the iStar 2.0 guide (§8) and blocked valid models, also on import. Before writing a conformance rule or its test, quote the guide/Table 1 clause it comes from; if no clause forbids it, it is not a conformance error. Differential-probe both validators (Rust and TS) against the guide when touching them, and keep them in parity.
8. **Every write path validates, not only the "add link" ones**: `ModelService::add_link` / `add_dependency` and the store's `addLink` were guarded, but direct writes (agent `UpdateActor` / `UpdateElement` / containment, store `updateActor` / `updateElement` / `moveElementBy`) could silently leave a model non-conformant. Direct writes go through an atomic guard (`apply_checked` in `agent.rs`, `introducedErrorClient` in `istarRules.ts`) that compares errors by `(rule, entity)` before/after and rolls back on a newly introduced error; pre-existing errors never block an unrelated edit.
